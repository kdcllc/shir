Decision (g8-library-ui-i18n): how the desktop app was internationalised.

Chosen: keep `apps/desktop/src/strings.ts` `STRINGS` as the flat English source of truth (scripts/desktop-contract.test.ts parses it against docs/DESKTOP.md) and add `TEMPLATES` (i18next `{{var}}` + `_one/_other`) for the former helper functions; the EN resource is `{...STRINGS, ...TEMPLATES}` and HE (`src/i18n/he.ts`) must cover every key plus `_two/_many` plural variants, guarded by a parity test and an independent g8 contract test. A dedicated i18next instance (`createInstance`) is initialised synchronously before render in main.tsx (detect → init → apply `<html lang dir>`); `setLocale` changes language, stores `shir.locale` and applies the document direction; detection alone never stores. All resource keys for the whole goal were frozen in the contract task so later tasks never edited he.ts. Messages kept in React state are `{key, vars, detail}` translated at render (`say()`).

Alternatives considered: an in-house typed dictionary with a `useT()` hook (no dependency, compile-time keys) — rejected because i18next was already pinned in STACK.md and gives plurals/interpolation; nested/renamed keys — rejected to avoid churn in ~30 components and the desktop contract test.

Consequences: English output stayed byte-identical; tests that assert English text kept working; Hebrew plural `_many` is unreachable in Node's ICU but required for older WebKitGTK ICU, so it is checked by reading the resource directly.

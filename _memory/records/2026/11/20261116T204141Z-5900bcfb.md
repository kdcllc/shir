Two test and runtime traps found while hardening the webview error forwarder (g5b-backlog, apps/desktop/src/webviewErrors.ts):

1. A vitest `vi.fn(() => Promise.reject(…))` spy marks the promise it returns as handled, because the spy attaches handlers to track settled results. A test that checks "the forwarder swallows a rejecting log" therefore passes even when the `.catch` is removed. Use a plain function, and wait a macrotask (`await new Promise(r => setTimeout(r, 0))`) so vitest's run-level "Unhandled Rejection" fails the run. Note that this guard shows up as exit 1 and an "Errors" count, not as a failing test.

2. In WebKitGTK/JavaScriptCore (the Linux Tauri webview), `Error.stack` holds only the frames, with no "Name: message" header. V8/WebView2 (Windows) includes the header. Code that logs `err.stack ?? err.message` therefore loses the message on Linux. Build the text as `name: message` plus the stack, and add the header only when the stack lacks the message. jsdom/V8 tests cannot see this, so pin it with a test that overrides `stack` with a frames-only string.

Also, `eprintln!` panics when the stderr write fails (EPIPE). Any IPC command that logs must use `let _ = writeln!(std::io::stderr(), …)`.

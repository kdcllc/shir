Decision: in chord-render, each chord anchor is a span that WRAPS the grapheme it sits on (`<span data-anchor data-index=i>{grapheme}<span data-chord-box dir=…>{chord}</span></span>`); the chord box is absolutely positioned (inset-block-end:100%, inset-inline-start:0) and the inner `<bdi dir="ltr">` chord symbol is never positioned. Rule B3 in .claude/skills/hebrew-rtl-chords/SKILL.md was amended to match.

Alternative considered: zero-width anchor spans inserted between text segments (original B3). Rejected because a zero-width element at a bidi run boundary (e.g. LTR run inside an RTL line, or line end) has an ambiguous visual position — browsers place it on either side of the run, so chords land over the wrong letter and differ between Chromium and WebKit.

Consequences: anchor x equals the grapheme's own inline-start edge in both engines (checklist 2 ≤ 2px); the lyric text excluding chord boxes still equals the source line; anchors past the last grapheme (chord at end of line) still need their own handling (backlog).

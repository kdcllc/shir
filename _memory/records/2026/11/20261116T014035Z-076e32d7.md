Pitfall: guarding tests that pass under the very mutation they exist to catch. In G4, evaluators running scratch-copy mutations found at least nine such guards across tasks 03–06, each costing a fix cycle; every one looked correct on reading.

What went wrong (patterns to recognise):
- A second constraint masks the one under test: a STRICT-typing test inserted 'abc' as capo, but the capo BETWEEN 0 AND 24 CHECK rejects TEXT anyway, so removing STRICT still passed. Use a value only the guarded rule rejects (1.5).
- Natural data order hides a tiebreak: UUIDv7 ids rise with insert order, so dropping `id DESC` (or `updated_at DESC` when ids correlate) changed nothing. Construct data where only the guarded key yields the expected order.
- Tests written relative to the constant: SEARCH_LIMIT=101 still passed because the test inserted LIMIT+1 rows. Pin the literal value too.
- ASCII-only boundary data cannot tell bytes from chars; use multi-byte Hebrew at the 1 MiB boundary.
- Clock-dependent formatting: a fixed-width timestamp test only failed when the wall clock had ms < 100. Test the formatter at fixed instants.
- "Exactly N" asserted as "contains N"; an always-write sync passed a test that only checked the final content.
- Missing boundary cases (capo lower bound 0/-1) and missing negative controls (MATCH on an absent term).

How detected: evaluators applied named mutations (M1…M25) in a scratch copy with its own CARGO_TARGET_DIR and required "only the target test fails".

Avoid: for every requirement-named behaviour, state the mutation the test must catch and run it before reporting; implementers should record test-ladder proof records (edit file:line, command, FAIL line, target-only evidence, PASS after restore). Equivalent mutations (removing a pragma whose bundled default is identical, e.g. foreign_keys/busy_timeout in rusqlite) are not defects — mutate the value instead.

Goal g11-doc-import-ai: outcome shipped (branch feat/g11-doc-import-ai, PR pending user approval).

Delivered: a 19th Tauri command `extract_document(path)` (async, spawn_blocking) that extracts text from .docx, .odt, .rtf and text PDFs in Rust (crates zip 9.4.2, quick-xml 0.42.0, encoding_rs 0.8.44, pdf-extract 0.12.1; 20 MiB file cap, 2 MiB extracted-text cap; typed DocErrorKind TooLarge/TextTooLarge/Unsupported/Corrupt/Io). chord-core gained documentToText (blocks → text, chord lines above Hebrew rewritten in display form and right-edge aligned, rtlColumns "mirror" for every format), buildAiPrompt (copy-prompt for any chat AI, text or attach mode, self-checked RTL worked example) and parseAiReply (fences, `{new_song}` split, 500-song cap). Desktop: Open files accepts documents and always queues them for review; a new Import with AI dialog (copy prompt, paste reply, review each song); Editor "Convert with AI" that only asks to discard after real edits. Real-app WebdriverIO E2E, Rust integration tests over all fixtures and a g11 contract test with negative self-tests.

Key decisions: copy-prompt workflow, no API calls; local extraction for docx/odt/rtf/text-PDF, attach-to-AI for images, scans and .doc; documents never auto-saved; a hand-written RTF tokenizer; a Hebrew/Arabic \fcharset beats \ansicpg (found only in the final audit).

Remember next time: 89 follow-ups were logged, about 64 still open (PDF ActualText recovery, test-fixtures readers broken under jsdom, \af fonts in RTF, setlists e2e title colliding with a seeded song). Ready groups pairing one Rust and one TS task worked well. Evaluators caught three plan-level defects in the RTL chord model and the prompt wording before code was written.

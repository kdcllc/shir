Pitfall: workflow_run release workflows with contents:write are easy to make injectable, and the obvious guard greps miss it.

What went wrong (caught at planning, Phase 3): the first plan had the release script's `reason` output name the PR branch, and the workflow echo it into $GITHUB_STEP_SUMMARY. A fork PR branch such as `chore/$(curl…|sh)` is a legal ref, so `echo "${{ steps.plan.outputs.reason }}"` in a run: block is shell injection in a privileged workflow. The planned guard grep only matched `github.event.*` expressions, so it could not see step-output interpolation.

How detected: the Phase 3 evaluator re-ran the grep on a sample with `${{ steps.plan.outputs.reason }}` inside a run: block (no hit).

How to avoid: forbid every `${{ }}` inside run: values (pass values through env: or files); build script outputs from fixed text, version tags and PR numbers only; have the script write the step summary itself. Guard it with a run-value scanner that handles inline `run:`, `- run:`, `run: |` / `run: >` blocks, and plain multi-line continuations — the key-column indent is the block boundary (anchoring on the `-` column falsely flags a sibling `env:`). Two awk drafts were wrong before the third passed TN/TP; prove every scanner on block, inline and folded samples.

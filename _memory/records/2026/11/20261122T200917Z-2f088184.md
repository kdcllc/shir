Pitfall: RTF code page precedence — \ansicpg must not override a Hebrew or Arabic font charset.

What went wrong: the g11 RTF extractor (apps/desktop/src-tauri/src/commands/documents/rtf.rs) first followed a spec that let `\ansicpg` always win. Pre-Unicode Hebrew RTF from WordPad/RichEdit declares `\ansicpg1252` with a `\fcharset177` font and writes `\'hh` bytes, so "שלום" decoded as cp1252 mojibake "ùìåí". The spec also mapped \fcharset178 (Arabic, cp1256) to Hebrew cp1255. Fixtures generated by LibreOffice write `\uN`, so no fixture exposed it; it survived task evaluation and was caught by the final audit.

How to avoid: per run, the font's charset decides first (177/181 → 1255, 178–180 → 1256), then `\ansicpg`, then 1252. Real-world byte-encoded Hebrew RTF is not covered by soffice-generated fixtures; add a hand-written `\'hh` case whenever touching RTF decoding. Still open: `\af` associated fonts under `\rtlch` are not tracked.

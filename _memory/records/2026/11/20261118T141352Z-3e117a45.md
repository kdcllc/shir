Decision: the visual song editor edits ChordPro text through chord-core edit operations; it does not keep its own document model (goal g7-visual-editor-delete).

Decision: songs stay stored and edited as ChordPro text. The Visual tab parses the text (`parseSong`), renders rows with the read-only renderer's editing mode, and turns every user action into an `EditOp` (17 types, packages/chord-core/src/edit.ts). `applyEdits(song, ops)` applies them, serializes and reparses, and returns `{ song, text, changed }`. The editor shell pushes `text` into one history (`useHistory`) shared by the Visual tab, the Source tab, the song-details form, transpose and the import tools.

Alternatives considered: a separate rich document model for the visual editor with conversion on save (rejected: two sources of truth, lossy for tab blocks, unknown directives and malformed input); contenteditable over the rendered song (rejected: bidi caret behaviour and chord anchors are not controllable); a Rust-side edit API (rejected: no IPC change was needed).

Rationale: lossless by construction — lines the visual editor does not understand are shown verbatim and survive untouched; an unedited song saves byte for byte; undo/redo, dirty tracking and the Source tab work on the same text; chord positions are logical grapheme indices, so Hebrew, niqqud and mixed lines need no visual-column storage.

Consequences: the first visual edit may canonicalize the text (for example CRLF to LF); per-line direction does not survive the reparse (rely on song direction and `lineDirection`); typing `[`, or a leading `#` or `{`, in a lyric turns the row into a verbatim row; UI state that holds line indices must be reconciled whenever a new song arrives (`reconcileUi`, `lineMap` in apps/desktop/src/visualKeys.ts).

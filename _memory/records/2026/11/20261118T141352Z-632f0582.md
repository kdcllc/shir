Pitfall: jsdom-green UI with defects that only a real browser engine shows (goal g7-visual-editor-delete).

What went wrong: three defects passed every unit, integration and contract suite and every task-level evaluation, and were found only by probing the built desktop app in Chromium and WebKit.
1. Print: `@media print { [data-ui-chrome] { display: none } }` tied on specificity with component classes that set `display: flex/grid` and came earlier in the bundle, so toolbars, the song list and dialogs printed. A source-text test of the rule cannot see a lost cascade.
2. React keys: visual-editor rows were keyed by raw line index. A song-details commit that inserted a directive line shifted every key, remounted all rows between mousedown and click (the click was swallowed) and left the open chord picker pointing at the neighbouring line.
3. Layout effect dependency: the chord overlap pass depended only on the song object, so a row remounted by leaving lyric-edit mode without a text change lost its overlap padding (27 overlapping chord pairs on a dense Hebrew row).

How it was detected: evaluators built the app into a scratch copy (`vite build`), stubbed the Tauri `invoke`, and drove it with Playwright (print media emulation, real mouse clicks, bounding-box overlap counts).

How to avoid it: when a goal adds interactive UI in apps/desktop, give the test task a real-engine check of the built app (not only the chord-render harness, which mounts `EditingSong`); key list rows by an identity that survives insertions above them; when UI state holds line indices, decide explicitly how it follows or resets on changes from outside the component; make global "hide" rules win the cascade (`!important`) and verify with computed style in a browser.

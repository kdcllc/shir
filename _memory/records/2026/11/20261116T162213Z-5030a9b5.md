Pitfall: recorded mutation proofs can be wrong even when written in good faith. Evaluators must re-run them.

In G5 the closer's test-writer reported that bypassing the "already seeded" flag check made the seed-once test fail. The evaluator re-ran it and all tests passed: the second seed hit the app_meta PRIMARY KEY, rolled back, and only logged "seeding failed". The same report also mis-stated another proof as "not target-only".

Fix: the test now also asserts that a direct seed_bundled after reopen returns Ok(0). That makes the bypass detectable even when a constraint masks it.

Related G5 findings of the same shape:
- A task file's own mutation line (renaming a struct field) was vacuous because it breaks compilation; a serde rename is the behavioural equivalent.
- A contract test's "negative control" asserted on its own edited input and could never fail.

Avoid:
- For every guarding test, name a mutation that changes behaviour (not compilation) and that no other constraint or default masks.
- Run it in a scratch copy and record the exact failing line.
- Evaluators re-run at least one recorded proof per task, and treat "does not reproduce" as blocking (task-criteria F3).

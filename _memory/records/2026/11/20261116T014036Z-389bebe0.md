Decision (G4 storage design): niqqud-insensitive search uses a plain FTS5 table `songs_fts(title_norm, artist_norm, lyrics_norm)` whose rowid equals `songs.rowid`, written by Rust (normalize_he) in the same transaction as the `songs` row — not an external-content FTS table with SQL triggers.

Alternatives considered: (1) external-content FTS5 (`content='songs'`) with triggers — rejected because triggers cannot run normalize_he without registering a custom SQL function, and normalization must be byte-identical for stored text and queries; (2) normalized `*_norm` columns on `songs` plus FTS — more storage, same sync problem.

Rationale: one Rust normalize_he for both sides; the original ChordPro, title and artist stay unmodified in `songs` (niqqud is stripped only in `*_norm` columns, per hebrew-rtl-chords).

Consequences (must hold in every later goal):
- `songs` has a TEXT primary key, so its rowid is implicit and SQLite may renumber it on VACUUM or a table-rebuild migration: never VACUUM, or rebuild `songs_fts` from `songs` afterwards; any table-rebuild migration must rebuild the FTS rows.
- Updates must use UPDATE, never REPLACE / INSERT OR REPLACE (that changes the rowid and orphans the FTS row); deletes remove both rows in one transaction.
- Tests guard this: update-keeps-rowid, count(songs_fts)==count(songs), and a REPLACE mutation must fail them.
- Queries replace non-alphanumerics with spaces (matching unicode61 tokenization), quote each token as a prefix term and bind the MATCH expression, so FTS syntax cannot be injected.

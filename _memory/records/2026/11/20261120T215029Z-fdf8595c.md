Decision (g10-setlists): Word (.docx) export of chords over Hebrew/English lyrics is built as tables of single-direction cells, sized from real font metrics, with chord paragraphs never bidi — not as ruby annotations or monospace chord lines.

How it works: chord-core export.ts directionalCells() splits each lyric segment at direction-run boundaries (Hebrew strong RTL, Latin/digits LTR, neutrals resolved by neighbours) in logical order; the docx builder (apps/desktop/src/export/docx.ts) emits one column per cell, w:bidiVisual + table jc=right on RTL lines, reverses only whole opposite-direction cell groups (never strings), sets w:rtl only on RTL cell runs, gives chord paragraphs no w:bidi (so "F#" stays LTR) aligned right in RTL cells with the 100-twip end margin on the cell's visual end, and sizes columns via estimateColumnWidths() from Liberation Sans hmtx tables (fontMetrics.ts, metric-compatible with Arial) × 1.1 + 60 twips.

Alternatives considered: one column per chord segment (rejected: reorders mixed lines, B3), docx equal-split columns (rejected: ~2 cm gaps inside words in LibreOffice), bidi isolates around chords (rejected: would distort width estimates), w:ruby (docx 9.15.2 support unverified).

Consequences: verified in LibreOffice 7.3 only; Word's reading of w:tcMar inside w:bidiVisual and of table jc is unverified; long lines stay one table row (no wrap); an rtl chorded cell followed by an ltr chorded cell in an ltr line lets the two chords touch.

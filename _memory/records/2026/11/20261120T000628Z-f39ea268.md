Decision: releases aggregate every unreleased merged feat/ or fix/ PR since the latest v* tag, instead of releasing per merge commit.

Context: release.yml runs on workflow_run after CI succeeds on main. ci.yml uses `concurrency: ci-<workflow>-<ref>` with cancel-in-progress: true, so any push to main during a merge's CI cancels that CI run. This happened on PR #9 (merge c48e1f0 cancelled by a chore(memory) direct push 7 minutes later). A per-merge rule would silently never release such merges, and a workflow-level release concurrency group drops pending runs too.

Alternatives: per-merge rule plus a "no direct pushes after merge" process rule; accept and document the drops; release-please style release PRs.

Rationale (user-chosen, Phase 3): aggregation is self-healing — any later green main run picks up everything since the last tag, so cancelled CI and dropped pending release runs only delay a release. The bump is the max label over the included PRs.

Consequences: a direct push can trigger a release, but only when it carries unreleased feat/fix merges. Two guards are required: a commit already tagged is never re-released (CI re-runs are idempotent), and a commit that is not a descendant of the latest release tag never releases (a re-run on an old commit cannot move Latest backward). The plan job fetches `/commits/{sha}/pulls` for every first-parent commit since the tag; any API failure fails the job rather than dropping a PR.
